# M3 final completion plan and adversarial review

2026-09-21. Implementation follows this plan; completion requires the resulting gates.

## Integrity and shared quarantine proof

Verified files/identifiers: sqlite RowDigest.add/read, SqliteEventStore.rewrite,
writeShard, quarantineShard; storage testFixtures EventStoreContract.open;
SqliteEventStoreContractTest.open. Extend the canonical encoding with an additive
modulo-2^128 sum of per-row SHA-256 prefixes, with multiplicity counted separately.
Compare independently read output against input, never just insert bindings.
Add backend-supplied quarantine fault hooks to the inherited contract and test
failure leaves rows and gaps intact, then successful retry and reopen refuse reads.
Attack: XOR cancels paired duplicates; explicitly test adding the same row twice.
A count alone misses substituted payloads; test equal-count different payloads.
Does not prove resistance to malicious manifest replacement or all hash collisions.

## Incremental maintenance

Verified SqliteEventStore.compact/boundedRewrite, seal/writeShard, verify,
MaintenanceControl, MaintenanceSchedule.tick and StoreConsumer.maybeSeal.
Introduce a separate cooperative step API, with a retained unpublished job and
keyset progress across calls. Seal and compaction copy bounded row chunks, verify
inputs and output incrementally, and publish only at completion. The consumer drains
between calls. Explicit destructive operations invalidate unpublished jobs rather
than let stale outputs resurrect removed rows. Interrupted processes discard
unpublished work safely; live-process yielding must retain progress.
Attack: shard ids can be stolen by an intervening seal; use unique unpublished file
names and assign ids at publication. No cross-call manifest transaction or hot
reader snapshot may prevent append/checkpoint progress. A cancellation is not
corruption. Never quarantine because a budget elapsed. Tests must assert progress,
completion, cancellation, interleaved append, invalidation and reopen branches.
Filesystem stalls and a single native I/O operation remain outside hard deadlines.

## Verification and WAL lifecycle

Add incremental scheduled content verification using the same canonical digest,
keyset traversal and explicit healthy/unverified/quarantined outcomes. Checkpoint
on the consumer maintenance path with a nonblocking busy policy, report pending
readers and retry after release. Test a reader-held WAL and actual completed retry;
a pragma being issued is insufficient. Keep full explicit structural verification.
Attack: a long-lived verification snapshot can pin WAL; sealed-file readers must
not retain a manifest snapshot. A completed content scan is not SQLite's full
integrity_check or a power-loss proof.

## Measurement and completion ledger

Extend committed MaintenanceCosts/M3Evidence and serial pinned-server scenarios
before measuring. Record seal/verification work and incremental progress alongside
capture backlog/drops; retain raw outputs generated by MeasurementRun. Real-server
tick impact must use the harness's existing tick sampler, with workload and scope
explicit. No private database re-walk is needed for this maintenance change.
Update ROADMAP, ADRs and completion audit only after their named gates pass; retain
historical limitations and do not promote M4. Build, module graph, formatting and
README evidence checks precede signed-off local commits. Never push.
